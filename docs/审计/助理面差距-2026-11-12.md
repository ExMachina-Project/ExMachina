# 助理面差距矩阵（2026-11-12）

> 来源：agent-parity-quality-2 task 2.6。方法：代码现状扫描（五维逐条文件级佐证）× 2025–2026 主流产品对标（websearch），产出差距矩阵与 Top N 建议。
> 定位基准：ExMachina = 自托管个人 AI 助理（Rust 核心 + OpenAI 兼容可换厂商 + 多 IM 通道 + WebUI）。对标系：ChatGPT / Claude / Gemini / Perplexity / 豆包 / 文小言 / 扣子 / Open WebUI / LobeChat / GPT-Researcher。

## 2026 助理面基础预期线

对任何「个人 AI 助理」定位产品（含 IM 机器人形态）的默认预期，按刚性排序：

1. 跨会话记忆且面板可见可删（最刚性底线——没有记忆的助理不成立）
2. 对话内生图（「会聊天」的一部分）
3. 语音输出（至少 TTS 朗读）
4. 带引用的深度研究（计划→并行搜索→引用报告→可导出四件套）
5. 自然语言定时任务（说「每天 8 点给我天气」即建即确认即推送）

## 维度 1：多模态输出

**结论：部分有——文件/截图出站链路完备；TTS 有引擎无出口；图像/视频生成完全缺失。**

### 现状

| 能力 | 状态 | 证据 |
|---|---|---|
| TTS 引擎 | ✅ 有 | `provider/mod.rs:367` speak() trait；`compat.rs:769-781` openai/azure `/audio/speech`（mp3）；`orchestrator.rs:287` speak_audio() 槽位链 |
| TTS 出口 | ❌ 断 | `POST /api/voice/speak`（voice.rs:44）存在但 webui 无组件调用（`.speak-btn` 孤儿 CSS）；outbox 全部调用点只有 `"image"`/`"file"` 两类——**无任何路径产出 voice**，而 telegram sendVoice / napcat record 出站通道已实现（telegram.rs:437-481、napcat.rs:1076-1118） |
| 图像生成 | ❌ 无 | 全仓库无 image_gen/generations 封装；图片产物仅来源浏览器截图（browser.rs:87）与屏幕截图（computer.rs:51） |
| 视频生成 | ❌ 无 | — |
| 文件出站 | ✅ 全 | outbox→run.finished artifacts→`media_fallback` 平台直发/降级（reply.rs:132-172、channel/mod.rs:198-240）；send_file 双入口（files.rs:846、napcat_tools.rs:246） |
| 多模态输入（对照） | ✅ | images data URL 三协议组装（compat.rs:344-425）；会话级暂存 image_stash；webui 压缩上传 ≤1280px×4 |

### 主流对标

- 生图与 TTS 朗读是基础预期（ChatGPT GPT Image + GPT-Live 默认、Gemini Nano Banana、豆包/文小言均默认）；实时语音对话为头部标配二线加分；视频生成仍是付费加分项（Veo 3.1 / Seedance）。
- 自托管事实标准：**旁路 OpenAI 兼容端点**（ComfyUI/SD/Flux 暴露 `/v1/images`、TTS 走 `/audio/speech`），核心 LLM 与多模态生成解耦——与本项目「可换厂商」架构天然契合。

### 差距

1. **G1.1 voice 产出链断裂**：引擎/出站通道/前端封装三者齐备，唯独无生产者把模型回复转语音进 outbox——补一小段接线即通（性价比最高的一格）。
2. **G1.2 无图像生成工具**：模型不能应「画一张」出图；缺 provider 层 generations 封装 + image_gen 工具 + outbox 投递。
3. G1.3 无视频生成（加分项，暂不追）。

### 优先级

**G1.1 高**（三缺一，收口即达 2026 基础预期线）；G1.2 中高（需 provider 封装，依赖用户配置生图端点，收益大但工作量独立成任务）；G1.3 低。

## 维度 2：Artifacts 类型

**结论：部分有——文件产物卡 + Markdown/代码块/diff/DAG 卡齐全；无 canvas 产物面板、无图表/公式渲染。**

### 现状

- 产物管线：outbox→artifacts→平台直发（同维度 1）；webui image 缩略图卡/file 下载卡（ChatView.tsx:97-118）+ `/api/asset` 内联预览与 download。
- Markdown：ReactMarkdown + GFM 表格 + CodeBlock 语言标签/复制/14 行折叠/裸 JSON 包围栏（Markdown.tsx:52-137）。
- 结构化卡：diff 审查卡（ToolCall.tsx:74-94）、编排 DAG（TaskGraphDag）、计划卡（PlanCard）、导出 markdown/json/trajectory（sessions.rs:751-858）。
- IM 长文本整形：代码块不可分单元 + 段落边界优先（channel/mod.rs:268 split_reply）。

### 主流对标

- Claude Artifacts 侧栏面板是标杆；**ChatGPT Canvas 已于 2026-05 下线，转向「artifact 文件化」**（writing/code blocks + 任务产物文件查看器）——方向是产物即文件进工作区，而非纯预览面板。
- IM 降级形态主流组合拳：文件发送 + Markdown 感知分块（QQ 官方 SDK 内置 chunkMarkdownText）+ 图表/HTML 渲染成图发送 + 链接回 Web 预览（LangBot 等自托管项目普遍做法；QQ Bot 官方 Agent 接口支持文字/语音/图片/视频/文件上下行）。

### 差距

1. **G2.1 无图表渲染**：mermaid/echarts/KaTeX 全无依赖——模型输出 mermaid 代码块只当代码展示，IM 端更无从谈起（渲染成图发送是主流降级）。
2. G2.2 无产物聚合视图：一次会话多产物无清单页（api/workbench 文件树只服务 @ 提及）。
3. G2.3 无 iframe 沙箱预览（html/svg artifact 只有下载形态）。

### 优先级

G2.1 中（webui 加 mermaid 渲染是纯前端收益，IM 端需服务端渲染管线，后者工作量大）；G2.2/G2.3 低（「artifact 文件化」趋势下，既有文件下载卡已踩在主流方向上）。

## 维度 3：深度研究（Deep Research）

**结论：部分有——搜索聚合/子代理并行/研究链 playbook 齐全；无多轮研究编排、无引用管理、无报告产物。**

### 现状

- 搜索底座强：多后端聚合 web_search（权重合排/去重/includeContent，2.4 产物）+ 浏览器搜索兜底（browser.rs:93-113）+ 主动搜索纪律（autonomy.rs:115-133，时效问题先搜、2 轮换词上限）。
- 子代理并行：tool_spawn 独立上下文只读白名单（spawn.rs:11-120），schema 明示「适合全库检索、批量调研」。
- 研究链 playbook：entities/groups/exmachina/playbooks/research.json 四步研究链（背景补齐→方案比对→假设管理→汇报收束）。
- web_fetch 正文提取 + 外部内容隔离（web.rs:68-111）。

### 主流对标

- 开源 DR 参考架构（GPT-Researcher / LangChain ODR / Local Deep Research 共同模式）：**规划器 → 并行子 agent → 压缩回灌 → 带引用报告**；breadth/depth 可配的递归研究树。
- 商业标配四件套：可编辑研究计划、过程可见、内联引用 + 来源清单、报告导出。

### 差距

1. **G3.1 无多轮研究编排器**：搜索→阅读→反思→再搜索的循环无封装（依赖模型自觉 + unit_max_steps=16 通用上限）；spawn 单层（spawn.rs:46 剔除 Spawn）不能树状分叉。
2. **G3.2 无引用管理**：多轮来源无聚合为引用列表的机制（EvidenceItem 服务于会话证据等级，非报告引用）。
3. G3.3 无报告结构化产物（研究结论只进 statements 文本，无「报告文档 → outbox 投递」模板链路）。

### 优先级

G3.1/G3.2/G3.3 各自工作量都不小且相互耦合，**合并为一项中优先级**（有 playbook + spawn + 聚合搜索的底子，本质缺一个「研究模式」编排封装；建议入 backlog 作为独立 change 立项，不挤占本轮）。

## 维度 4：定时任务 NL 化

**结论：部分有——schedule 工具在、对话创建链路通；但 cron 靠模型裸算、调度无时区、工具建的任务不能推送结果。**

### 现状

- 模型工具：tool_schedule（op=create/list/remove/enable/disable，schedule.rs:7-146），schema 描述明示「每天巡检/明天提醒跟进」自驱用法——**用户自然语言提需求、模型换算 cron 调工具，链路存在**。
- REST/WebUI/CLI 全套：CronBody 完整字段（cron/at/kind=target_session/steps=queue/group/session_title/enabled/notify_channels，cron_admin.rs:7-36）；表单含 5 个 cron 模板一键填入；CLI `--cron/--at/--kind queue --steps`。
- 调度器：20s tick、一次性触发自动停用、心跳/AutoAgent/MetaAgent/闲置归档/记忆摘要同循环；结果推送 notify_channels 双闸门 + 退避重试。
- 事件触发器族：文件监听（glob+去抖）+ event_webhook（HMAC→EventTrigger→注入）。

### 主流对标

- ChatGPT Tasks / Gemini Scheduled Actions / 扣子 / 豆包任务模式均纯 NL 建任务；**「用户永远不接触 cron 表达式」是 2026 共识**，回显确认（把解析出的规则+下次执行时间告诉用户）是最佳实践；时区自动处理是基础预期（QClaw 明确「自动生成定时规则、自动设时区」）。

### 差距

1. **G4.1 schedule 工具残缺**：`notify_channels: Vec::new()` 硬编码（schedule.rs:62）——**模型建的任务无法订阅结果推送**；也不支持 target_session/steps/queue（构造时全空）。「每天 8 点把天气推到我 QQ」这条主链路，模型工具面走不通，只能去 WebUI 表单建。
2. **G4.2 无时区**：调度全按 UTC（cron.rs:27 Utc::now、cron_scheduler.rs:27）；AutomationConfig 无 timezone 字段；用户说「每天早上 8 点」，模型若写 `0 8 * * *` 实际北京时间 16 点触发（at 支持 ISO8601 带偏移，cron 不支持）。
3. G4.3 无 NL 辅助/回显确认：cron 换算完全依赖模型算术，工具返回不含「下次执行时间」预览（REST list 有 nextRunAt 前扫，工具 create 返回没有）。

### 优先级

**G4.1 高**（一行硬编码缺口 + 几个透传字段，补齐即打通「NL 建任务→结果推送」主链路）；**G4.2 高**（中国用户主场景全部偏 8 小时，属正确性缺陷而非功能缺失）；G4.3 中（跟随 G4.1 顺带在 create 返回里加 nextRunAt 回显即可达成最佳实践）。

## 维度 5：记忆管理增强

**结论：有——六类记忆 + 混合检索 + 衰减 + 模型自主写入 + 面板查看/删除/置顶齐全；缺条目编辑、自动衰减、导出。**

### 现状

- 存储：MemoryStore（倒排 + 哈希索引 + links + agent_stats）；六类记忆类型加权；词项+语义混合检索（无命中语义兜底）；可插拔 Embedder。
- 治理：衰减半衰期 0.5^(age/half_life)（配置化）；同内容哈希去重提升；记忆链接（derived_from/contradicts/supersedes）。
- 写入：模型工具三件套 memory_read/write/link + LLM 自主记忆模式（实验）+ 每日低峰记忆归纳（实验）+ memory.md 文件记忆模式（可编辑）。
- 管理面：REST 全套（list/add/search/stats/reindex/decay/render/forget/pin/md）+ webui 记忆面板（统计卡/检索调试视角/kind+layer+agent 过滤/pin/forget）+ CLI 同套。

### 主流对标

- 基础预期：跨会话持久（全线标配）、面板可见可编辑可删、模型自主写入、可关闭/无痕；加分项：分层记忆（Project 级空间）、导入导出、API 级 memory tool（Claude Platform 目录式记忆文件范式）。

### 差距

1. **G5.1 无条目编辑**：REST 无 `PUT /api/memory/:id`，MemoryStore 无更新正文方法，面板操作列只有置顶+删除——改错记忆只能删除重加。
2. G5.2 衰减不自动化：decay 是手动端点，cron_scheduler 无周期衰减任务（半衰期配置了也要人点按钮）。
3. G5.3 无导出/备份端点。

### 优先级

G5.1 中高（用户可编辑是基础预期，但删除重加是可用替代路径，非断链）；G5.2 中（一行 cron 注册 + 复用既有 decay）；G5.3 低。

**Top 3 转任务（2.7 实施项）：**

1. **T1 定时任务 NL 主链路修复**（G4.1+G4.2+G4.3 打包）：schedule 工具补 notify_channels/steps/kind 透传 + create 返回 nextRunAt 回显；cron 调度加 timezone 配置（默认 Asia/Shanghai，cron 按配置时区解释）。验收：mock 下模型一句话建任务 → 任务带推送通道 → 下次执行时间为本地时区正确值。
2. **T2 语音回复产出链**（G1.1）：模型侧 voice 产出路径（按配置触发：显式工具 or 收束自动 TTS，取实现最轻者）→ outbox `"voice"` → 平台 record/sendVoice 直发 + WebUI 播放按钮接线。验收：mock 长会话产出 voice artifact；既有 speak 端点复用不新建。
3. **T3 记忆条目编辑**（G5.1）：MemoryStore 加 update 方法 + `PUT /api/memory/:id` + 面板编辑入口。验收：面板改一条记忆正文 → 检索命中新内容且 created_at/统计不变。

**入 backlog 不挤占本轮**：G1.2 图像生成工具（独立 provider 封装，建议单独立项）；G2.1 mermaid 渲染（纯前端可快赢但与本轮主线无关）；G3 深度研究编排（大项独立 change）；G2.2/G2.3/G5.3。
