# 子代理审计：竞态与并发正确性（2026-11-01）

> 来源：long-horizon-iteration task 1.3 并行子代理走查（只读）。范围：`crates/exm-core/src/`、`crates/exm-gateway/src/`。
> 已对照 subagent-audit-hardening 已修清单（该批为 REST 语义/运维项，与本轮并发主题无重叠）。

## P0 —— 零（两项专项核查）

- 锁序死锁：零。全部锁均为叶子级单锁使用，未发现跨锁嵌套（`ledger_lock` 内不再取他锁；`FsDb.lock` 仅护分桶读改写；`run_locks` 取出后立即释放 parking_lot 锁再 await tokio 锁；Core 各 RwLock 均为读快照→释放→再用）。
- 跨 await 持锁：零。Store/FsDb/MemoryStore 全同步方法无 guard 可跨 await；异步侧均 tokio::sync::Mutex；未发现 RefCell 跨任务共享。

## P1 —— 5 项

### P1-1 审批单双重执行（check-then-act + 跨 await 大窗口）
- 位置：`crates/exm-core/src/lib.rs:1459-1544`（`approval_decide`）
- 场景：双击「批准」或 WebUI+通道 plan:yes 并发：双双 get_approval 过 pending 检查 → 双双 await 执行（300s shell / plan_approve / video act）→ **命令执行两次**。status 仅在 await 结束后写回，窗口数分钟。
- 建议：进入先原子占位（update_approval 置 "deciding" 或 approval id 取 tokio::Mutex try_lock），失败方返回最新单据。
- 验证：并发两任务调 approval_decide 同一 id，断言命令执行次数==1。

### P1-2 全局交互上下文 switch→use→restore 无临界区（多通道并发必错组）
- 位置：`channel_runtime.rs:134-163`（switch_context_to）、`:729-783`（begin）、`:940-965`（restore）；同模式 `core/lib.rs:1722-1756`（run_event_prompt）、`:1759+`（run_cron_job）；底层 `registry.rs:309-316`
- 场景：激活组/单体是进程级全局态。通道 A begin 切 GA 后，通道 B begin 切 GB，A 随后读 active_scope 拿到 GB → A 的会话建到 GB、记忆分区错算；A 结束还原还把 B 的上下文覆盖。napcat/discord/matrix 每条消息 tokio::spawn，多通道并发是常态。WebUI 用户此刻建会话同样落错组。
- 建议：短期 begin 内 switch 后快照 scope 校验一致否则重试；中期目标上下文做成 ChannelRun 显式参数（不读全局 active），消灭全局切换。
- 验证：两通道并发 begin（不同 group），断言各自 session.group_id 与通道一致。

### P1-3 聊天流绑定 check-then-act + 读改写丢失 → 会话分叉
- 位置：`core/lib.rs:686-714`（flow_active_session/bind_flow_session 无锁 get→create→put）、`:728-740`（touch_flow_message 读改写）；调用侧 `channel_runtime.rs:741-765`、`platform/channels.rs:768-795`
- 场景：同 chat_key 两条消息并发：双双 flow_active_session→None → 各自建会话（S1/S2）→ 孤儿会话+绑定以后写者为准。更隐蔽：消息1 touch 预览读到旧快照（active=S1），消息2 bind(S2) 落盘后消息1 put 整体覆盖 → S2 绑定被抹，上下文永久分裂。store.rs:779-800 flow 三方法裸 fs 读写无锁无版本号。
- 建议：flow 文档按 flow_id 互斥（DashMap<String, Mutex<()>> 或复用 run_locks 模式），「查绑定→建会话→回写绑定」「touch 预览」各自临界区；最低成本 touch 只更新 last_message 且写回前校验 active_session 未变。
- 验证：同 chat_key 并发 20 条消息断言会话数==1 且绑定不变；现网征象 channel:* 会话异常增多。

### P1-4 通道回帖循环遇 broadcast Lagged 直接退出 → 回复静默丢失
- 位置：`channel_runtime.rs:1005-1030`（spawn_reply `while let Ok(evt)`）；同款 `platform/channels.rs:835-845`（webhook 回推）。对照：ws.rs:110 正确处理 `Err(Lagged(_)) => continue`。
- 场景：spawn_reply 内联 await 平台 API（秒级）期间不再 recv；rx 订阅全量 CoreEvent 广播（含 unit.token 瞬时流，一轮数千条）缓冲 8192；多单元并发流式+回帖阻塞慢 HTTP → Lagged → `while let Ok` 当流关闭 → **run.finished 收不到，用户得不到回复**（执行成功，纯静默丢）。
- 建议：与 ws.rs 对齐 `match rx.recv() { Err(Lagged(_)) => continue, Err(Closed) => break }`；进一步订阅端先按 session_id 过滤。
- 验证：灌入 >8192 条事件同时 send 闭包 sleep，断言循环存活并收到 run.finished。

### P1-5 atomic_write remove→rename 非原子窗口 + 确定性 .tmp 同路径并发 → 瞬时读空/文档损坏
- 位置：`fsdb.rs:291-299`（atomic_write 固定名 tmp 且 rename 前先 remove 目标）；`store.rs:102-110`（toggle_session_pin 无锁，与同族方法不一致）
- 场景A：remove 与 rename 之间读者 get() 得 NotFound → flow_active_session 顺手删绑定（会话分叉诱因）、REST 偶发 404。场景B：持锁 mutate 与无锁 pin 并发写同一 sessions/{id}.json 共用同一 {id}.tmp，交错后 rename 出半截 JSON。
- 建议：tmp 带唯一后缀（{id}.{new_id()}.tmp）；Linux 直接 rename 覆盖（POSIX 原子）仅 Windows 回退 remove；toggle_session_pin 补 ledger_lock。
- 验证：并发 put/get 各 1e5 次断言无 None/Err；pin+ledger 并发用例。

## 小结

| 维度 | 结论 |
|---|---|
| 锁序死锁 | 零（全叶子锁） |
| check-then-act | P1-1/2/3、P2-1/2/8 |
| 跨 await 持锁 | 零 |
| 全局态 | 单锁访问正确；问题在多锁组合（P2-8）与全局上下文本身（P1-2） |
