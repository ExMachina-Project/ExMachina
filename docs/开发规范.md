# 开发规范

面向所有贡献者（人类与智能体）：EXMACHINA 的分支模型、提交纪律、PR 流程与发版仪式。
本文是流程的唯一权威来源；与本文冲突的口头约定一律以本文为准。

## 分支模型

```
feat/* / fix/* ──PR──▶ dev ──发版PR──▶ main ──自动──▶ tag + GitHub Release
                        ▲                            │
                        └────────hotfix/* 修回◀──────┘
```

| 分支 | 角色 | 纪律 |
|------|------|------|
| `main` | **发版线**，永远等于「最新已发布版本」 | 只接受 dev→main 的发版 PR，禁止任何直接 push；一键更新从这里拉取 |
| `dev` | **开发线**，集成分支 | 只接受 PR，禁止直接 push（文档级小改可豁免，但不得含未测代码） |
| `feat/*` `fix/*` | 功能/修复工作分支 | 从 dev 拉出，PR 目标 dev |
| `hotfix/*` | 紧急修复分支 | 从 **main** 拉出，见下文 hotfix 流程 |

**核心不变量：dev 永远 ≥ main。** main 是 dev 在发版节点的投影，任何进入 main 的提交必须先存在于 dev。

## 提交规范

格式：`type: 中文描述——动机或后果`

```text
feat: 一键更新——POST /api/version/apply 经 docker.sock 执行 git pull→build→up -d
fix: 辅助容器挂载仓库宿主真实路径——/host 只存在于网关容器内
ci: 工作流触发策略收敛——CI 仅 PR 触发,发版仅 dev→main 合入触发
```

- **type 用英文小写**，描述用中文；`——` 之后写清动机、后果或实测数据，让半年后的读者不用翻 diff
- **一个提交只做一件事**：逻辑改动、格式化、文案调整不混在同一提交
- 类型清单：

| type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `perf` | 性能优化（附实测数据更佳） |
| `refactor` | 重构（行为不变） |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 构建/依赖/杂务 |
| `ui` | 界面布局与视觉调整 |
| `copy` | 文案措辞 |
| `rename` | 命名调整 |
| `build` | 构建系统/编排（Dockerfile、compose、脚本） |
| `ci` | 工作流与流水线 |
| `revert` | 回滚（注明回滚原因与回退路径） |

## PR 规范

1. **目标分支只有 `dev`**（唯一的例外：发版 PR 为 dev→main）
2. PR 合入前 **CI 必须绿**：`cargo check --workspace`、`cargo test --workspace`、`npm run build:webui`
3. PR 标题用主提交的 type 前缀；一个 PR 聚焦一个主题
4. 检查清单见 [CONTRIBUTING.md](../CONTRIBUTING.md)（契约文档同步、配置项入 schema 等）
5. 合并方式用 **merge commit**，保留开发线的完整历史脉络

## 版本与发版

- **版本号单一来源**：根 `Cargo.toml` 的 `[workspace.package] version`，其余位置一律引用或同步，不另立来源
- 遵循 semver；0.x 阶段 `MINOR` = 功能发布，`PATCH` = 修复发布
- **发版仪式（三步）**：
  1. 在 dev 上提交版本号 bump（随最后一个功能 PR 合入 dev）
  2. 发 PR：`dev → main`，标题 `release: vX.Y.Z`，CI 绿后 merge
  3. 完事——流水线自动：读版本号 → 打 `vX.Y.Z` tag → 构建三平台服务端预编译包 + 桌面端安装包 → 发布 GitHub Release
- **合入即发布**：一键更新的部署机会直接拉取 main。功能未经充分验证，不得合入 main
- **只合入不发版是合法操作**：不 bump 版本号直接 merge 到 main（如纯文档变更），流水线检测到 tag 已存在会自动跳过，不会重复发布
- tag 由流水线自动创建，**禁止手动打 tag / 手动发 Release**

## 工作流触发矩阵

| 事件 | ci.yml（编译+测试） | release.yml（构建+发版） |
|------|:---:|:---:|
| push 到 dev | ✗ | ✗ |
| push 到 main | ✗ | ✓（版本未 bump 自动跳过） |
| PR（→ dev 或 main） | ✓ | ✗ |
| 手动打 tag | ✗ | ✗ |

日常开发的每一次 push 都是零消耗的；验证关口在 PR，发布关口在 main。

## hotfix 流程

1. 从 `main` 拉出 `hotfix/xxx`（此时 main = 最新发版）
2. 修复并 bump PATCH 版本号
3. PR → `dev`（正常评审 + CI），保证 dev ≥ main 的不变量
4. 紧接着发版 PR `dev → main`，走标准发版仪式
5. 禁止绕过 dev 直接把 hotfix 提交推到 main

## Git 安全作业

与 `skills/git-safety.json` 约定一致：

- 禁止 force push 与任何 history 改写（`--force` / `reset --hard` / `clean`）；确需时先回流升级裁决
- push 前先 `git status` 确认提交范围，只推本任务相关分支
- 涉及共享分支（dev / main）的操作，先说明影响面与回退路径，并保留操作前 hash
