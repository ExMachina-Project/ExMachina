# 收拢协议


## 目的
- 把模糊请求收拢为可分派、可验收的任务：目标函数化、验收锁定、边界与禁区、未知清单、示例锚定。
- 收拢产出直接构成 OrchestratorPlan 的输入（`goal` / `acceptance` / `boundary`），是分解与派发的前置。

## 触发条件
- 需求边界不清、目标含混（「优化一下」「修好它」「处理一下」）时，必须先收拢再派发。
- L0 直达的纯交互与微操作不要求完整收拢；凡要拆节点（L1–L3）的任务必过收拢。

## 1. 目标函数化
- 把不可判定的说辞改写为可判定的目标句：**对象 + 期望行为 + 度量**。
- 目标句必须能回答两个问题：做没做到？用什么证据判定？
- 目标句写入计划 `goal`；节点的目标写入该节点 `objective`，一次说清，不留给子个体推断。

## 2. 验收标准锁定
- 每条验收标准可判定：给定输入，观察到的行为、输出或度量。
- 不可判定的验收词（更好、合理、尽量、流畅、优雅）必须替换为具体阈值或样例。
- 用户口头验收（「差不多就行」）转写为明确条款；转写结果有歧义时先向用户确认。
- 验收断言逐条写入 `acceptance`，一条一个判定点，不合并成一段话。

## 3. 边界与禁区
- 允许触碰：路径、模块、接口 → 写入 `boundary.inScope`。
- 禁区：不得改动、不得依赖、不得删除的部分 → 写入 `boundary.forbidden`。
- 未声明的默认是**只读**；实施类动作必须有显式授权。
- 「顺手修一下」的诱惑面要写进禁区，或作为独立节点显式立项。

## 4. 未知清单
- 列出当前不知道且影响验收的事实，逐条标注验证路径。
- 可由用户一句话回答的：直接问，不问第二次。
- 可由仓库证据回答的：列为侦察节点前置执行。
- 二者都不行的：作为假设随任务下发并标注 C 级（暂定假设）；收束时必须复核或显式保留。

## 5. 示例锚定
- 为目标行为至少锚定一个具体例子（输入 → 期望输出），作为验收样例与测试种子。
- 举不出例子的验收条款，视为未锁定，不得进入派发。

## 产出
- 目标句、验收条款、边界禁区、未知与假设、示例锚定——直接作为规划与简报输入。
- 缺项不允许静默进入分解：先补齐，或显式标注缺口后再派发。

## 禁止行为
- 用「更好 / 合理 / 尽量」等不可判定词充当验收。
- 未声明禁区就派发实施类节点。
- 影响验收的未知被藏起来，留到收束时才暴露。
- 把用户没说的意图当成已确认的需求。

## 自检问题
- 目标句能否被第三方独立判定真伪？
- 每条验收是否可判定、有无阈值或样例？
- 边界禁区是否覆盖了「顺手改动」的诱惑面？
- 每个未知是否有验证路径，或已标注证据等级？
