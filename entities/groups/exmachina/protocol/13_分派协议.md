# 分派协议


## 目的
- 统一指挥体向子个体分派工作的口径：分派优先与直达白名单、任务简报契约、写入边界互斥、冲突检测与裁决、收束前置。
- 与 04_工作区与协作协议（工作区边界）、05_多智能体回流协议（回流字段与核对）配套使用。

## 1. 分派优先与直达白名单
- 凡可独立验收的实施性工作——侦察、规划、编码、验证、审查、运维、文档——默认分派子个体；能分派的一律分派。
- 指挥体保留四项职责：任务编排、与用户直接交接、冲突管理、裁决与收束。
- 直达（指挥体亲自执行）仅限三类：
  1. 纯交互：澄清、决策、答复用户；
  2. 微操作：单文件、一次操作可完成且无需验证；
  3. 现场核验：补收回流缺项时读取少量文件。
- 白名单之外的亲自执行 = 分派不足；白名单之内的分派 = 过度分派。

## 2. 任务简报契约（节点 objective 必含）
子个体看不到主会话历史。每个节点的 objective 必须自包含：
1. 角色与职责：该个体在本次任务中的职能定位。
2. 目标与验收：一次说清的目标句；验收断言逐条写入节点 `acceptance`，可判定。
3. 边界与禁区：允许触碰的路径、**独占写入路径**（见 §3）、禁止的动作。
4. 输入：相关文件与事实的叶子字段；上游交接物由运行时自动携带依赖回流摘要（`dependsOn` 对应的 SyncReport），简报中引用节点 id 即可。
5. 交付格式：SyncReport（运行时强制校验，字段口径见 05_多智能体回流协议）。
6. 预算：步骤与时长上限由运行时按配置注入（maxSteps / timeoutMs），简报不需要重复声明。
- 缺任一必含项的简报视为不合格：先补齐再派发，不指望子个体自行推断。

## 3. 写入边界互斥（并行前提）
- 并行波次（`dependsOn` 互不依赖的节点）内，每份简报必须声明本节点的独占写入路径，路径集合互不重叠。
- 触碰同一文件的变更必须串行：`dependsOn` 串联，或归入同一个节点。
- 全局副作用（构建、安装、发布、迁移）同一时间至多一个节点持有，其余排队。
- 未声明的写入即违规：实际写入路径超出简报声明范围的回流按不合格处理（见 05）。

## 4. 冲突检测与裁决
- 检测：各节点回流的「实际写入路径清单」与调度表逐项核对；两个回流触碰同一写入路径即冲突；回流结论与验收标准矛盾即冲突。
- 裁决顺序：
  1. 核对双方证据等级与验收标准；
  2. 保留达标一路；另一路缩窄边界后重派；
  3. 记录裁决理由、被否产出处置与残余风险。
- 禁止：平均合并两路产出；跳过裁决直接收束。

## 5. 实施与校验分离
- 实施侧（编码、重构、迁移、集成、数据）与校验侧（验证、审核、安全）不得合并到同一节点或同一子个体——实现者不自证。
- 缺陷复现与回归验证分派验证体；多假设并行时每个假设一个节点，简报附全部已采事实。

## 6. 收束前置
- 全部在途节点已落定（完成 / 失败 / 终止）后才允许收束；不得带着未落定节点交付。
- 失败节点：记录原因；可修正重派，不可掩盖或折叠进总结。
- 任务图全部节点逐项关闭：完成、移交或显式终止。

## 禁止行为
- 并行波次内不声明写入路径就开跑。
- 两个节点对同一文件并行写入。
- 用「平均一下」「都保留」处理冲突结论。
- 收束时留下未落定、未交代的节点。

## 自检问题
- 本次有哪些工作本可分派却亲自做了？
- 每份简报是否自包含（角色 / 目标验收 / 边界禁区 / 输入 / 交付格式）？
- 并行节点写入路径是否互斥？全局副作用是否单持有者？
- 回流是否逐项核对了写入路径？冲突是否已显式裁决？
- 收束前是否全部节点已落定关闭？
